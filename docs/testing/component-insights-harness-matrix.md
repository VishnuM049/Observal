# Component Insights harness matrix: bounded Codex skill availability

This work is **stacked on draft #1779**, not a replacement for its verified-only installation contract. Discovery used temporary harness homes and an isolated loopback-only Compose project. No historical installation was inferred from current configuration, a transcript tool name, a skill mention, an Agent pin, or a manual reconcile. Raw sessions, credentials, arguments, prompts and provider responses are not fixtures or PR artifacts.

## Implemented cell

| Runtime/version | Installation and identity | Native activity | Delivery | Interpretation |
| --- | --- | --- | --- | --- |
| Codex CLI **0.163.0**, project-scoped skill | Tracked registry install writes `.agents/skills/<alias>/SKILL.md` with a version pin and content fingerprint. The layer hashes the active file, the pin's verification state and its canonical location, and checks for user/ancestor skill shadows. A matcher requires one resolved, verified, same-project/scope/alias/location snapshot at the source line. | Codex's native **developer** skills inventory supplies a rooted file location. The extractor records *available* only when a unique inventory names exactly `<session cwd>/.agents/skills/<alias>/SKILL.md`. It never reads user prompts, descriptions, skill contents, tool arguments or results for attribution. | A new native Codex session using the inert loopback scripted Responses provider arrived via vetted temporary `Stop` session-push hooks, without manual reconcile. | The first complete run had one verified-present session, one matched `available` fact and one *unmatched* fact from a separate untracked scratch skill. A second post-version-bump native run also arrived automatically and produced one matched `available` fact in a new complete publication. The prior publication was briefly stale after the version bump (coverage did not misread it as absence); after the isolated worker's bounded replay, the cohort had **two verified-present, two currently complete sessions, two published availability facts and two unrelated unmatched facts**. **Loads and invocations are unknown (null); observed use has no denominator.** Offering a skill is not proof it entered context. |

Only the exact recorded Codex version and POSIX absolute-path inventory are accepted; Windows paths remain unsupported until independently recorded. Missing or multiple native inventories, mismatched or repeated roots, repeated aliases, other project roots, home/ancestor skills, version changes, drifted/unverified pins, and mapping collisions never become attributed availability. A session on an untested version returns `unsupported`, not zero. No new MCP or hook cell is opted in. The developer inventory format and Mac `/private/tmp` canonical path variant are covered by sanitized fixtures; `tests/test_codex_skill_evidence.py` checks the verifier and same-hash matcher independently. CLI flags were not changed.

The skill summary now separates an **availability** projection from the **use** denominator. A fully projected Codex-only session can say `offered: 1`, while `confirmed_loads`, `loaded_sessions`, `load_attempts` and `invocations` are `null`, use rate is `null` and the attribution state is `attribution_not_possible`. When no session is fully projected, even availability is `null`. Mixed harness cohorts expose partial-kind reasons and only completely projected, use-capable sessions contribute to the usage-rate denominator. Server, CLI and web use this same published contract; the real worker-generated report and its desktop/mobile pages were exercised on the isolated stack.

## Other runtimes: observed, not opted in

- **Kiro IDE 1.3.11:** A real connected, **manually configured** user-scope inert MCP did execute `ping`; the native tool result contained the inert pong and an independent scratch marker confirmed execution. That configuration was **not** an Observal tracked install. Two subsequent IDE sessions (including the user's trust-and-chat control) were created with the standalone hook file under the project's `.kiro/hooks/`. The IDE registered all four hooks, but neither a prompt nor a silent post-tool marker appeared; both sessions were absent from Observal **before** manual recovery. A dry-run showed `2 would_push`, `4 up_to_date`; manual reconcile pushed the two without error. The isolated warehouse then had six IDE sessions / 87 events. This proves a parser and manual recovery, not automatic IDE delivery or a verified-present denominator. Earlier standalone user-home placement was incorrect for the IDE and was disabled; fixing that placement did **not** establish execution. Kiro CLI 2.32.0 is a separate runtime sharing the `kiro` registry key, so IDE-only evidence cannot safely make CLI sessions measurable.
- **Kiro CLI 2.32.0:** Real `ping` execution and a silent independent hook marker were observed in separate controls, but the transcript did not supply attributable MCP-install identity or per-hook execution identity. The tested standalone v1 hook did not fire on CLI 2.x. No verified cell.
- **Cursor Agent 2026.10.14:** Real accepted and rejected inert MCP attempts, skill-file reads and name mentions were controlled. MCP success/pong was in the live stream, **not** persisted JSONL; the persisted attempt cannot distinguish denial from success. A file read is not a native skill-invocation identity. Temporary delivery hooks sent four sessions, but did not record attributable component hook runs. No cell opted in.
- **Codex MCP/hooks:** Real provider sessions and vetted temporary hook markers demonstrated Codex's session delivery. An executed MCP `ping` was never established. A printed hook marker and a native developer-message output do not establish a registry hook's attributable execution identity. Explicit `$skill` expansion was recorded, but no native invocation-origin flag distinguishes that expansion from crafted user text, so `invoked` and `load` remain unsupported.

Tracked MCP `--apply` still supports Claude Code only. Extending it to these runtimes requires their native config formats, install receipts, shadow checks, ambiguity tests and a new live tracked delivery proof. Manual scratch MCP entries cannot supply the verified denominator. The Kiro IDE and CLI need distinct capability/projection handling before opting in IDE-only MCP or skill cells. Unverified versions and unsupported cells are **unknown**, never success, failure or measured zero.
