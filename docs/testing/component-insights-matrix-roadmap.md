## Gates before opting in another cell

1. **Binding:** a tracked registry install, selected version, active scope and file/command fingerprint in a contemporaneous same-user/project layer snapshot; fail closed on drift, shadows, duplicates or mixed Kiro runtimes. A manual config or Agent pin alone is not enough.
2. **Native signal:** controlled no-tool, denied, accepted, mention-only and unrelated-component runs must distinguish the proposed event *in persisted native records*, not only a live stream, stdout or independent marker. Bound versions and layouts need sanitized synthetic fixtures and ambiguity tests.
3. **Delivery:** demonstrate automatic arrival **before** reconcile, with source hash and publication version. Manual recovery proves only recovery. Use a loopback-only instance and temporary harness home.
4. **Projection and UI:** matched/unmatched/collision and stale/pending replay tests, correct null/partial denominators, API/CLI/report/browser checks. Do not turn unsupported cells or incomplete projections into zero.
5. **Privacy and review:** never ship prompts, tool arguments/results, raw transcripts, tokens or temporary profiles. Human review of code, screenshots and CI precedes ready/merge.

## Kiro CLI 2.32.0: tested scope and precedence

All controls used inert stdio servers in **new scratch workspaces**, the already isolated authenticated Kiro CLI home, a no-tool chat, and `--require-mcp-startup`. Scope-specific wrapper markers were absent before the chat and written only when that server process started. After correcting the inert server's test interpreter (an initial attempt lacked the local `mcp` package), each subsequent chat exited successfully; the native CLI removed the temporary aliases afterward, and the scratch home's originally absent MCP file was restored to absent. Nothing touched the user's real home or #1779. Startup proves a chosen process, **not an MCP `ping`, registry identity, or automatic delivery**.

| Scratch configuration with one colliding alias | Native behavior before chat | Process-start markers in chat |
| --- | --- | --- |
| `--scope global` and `--scope default` installs | Both wrote `~/.kiro/settings/mcp.json` (mode `0600`) in this CLI/home; `--scope workspace` wrote project `.kiro/settings/mcp.json` (mode `0600`). Native remove deleted only the selected entry. | Layout control only. |
| Home + project; default agent | `mcp list default` selected the **project** command; adding the home entry *last* did not change that. With the project alias removed, it selected the home command. | Project **yes**, home **no** for either write order; with project absent, home **yes**. |
| Agent profile + project + home, same alias | `mcp list workspace` showed the agent command, while `mcp list default` showed the project command and warned of duplicate configuration. `mcp list global` labelled merged config entries `legacy`; it is not a reliable file-origin readback. | With `chat --agent` both **agent and project** started; home did not. Setting `includeMcpJson: false` did not prevent this in the tested CLI. |
| Agent profile + home, no project alias | The agent list showed its own command; the home entry remained configured. | **Both agent and home started**. |

**Consequence:** project MCP configuration takes precedence over home MCP configuration for the default agent in this tested runtime, but an agent-local duplicate is **not** an override: the same alias can start twice. A tracked install cannot rely on `mcp list` alone to assert unique activity identity. The local tracked-install follow-up rejects collisions across agent, project and home; it claims no IDE capability or MCP-use extractor.
